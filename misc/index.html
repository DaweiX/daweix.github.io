12.1

  • Agentic AI vs. AI Agents review paper。Takeaway：AI Agent：执行特定任务的自主软件程序（e.g., 智能助手，聊天机器人），Agentic AI：多个 AI 智能体协作以实现复杂目标的系统（e.g., 供应链管理、业务流程优化、虚拟项目经理）

    Conceptual Dimension 生成式AI (Generative AI) AI 智能体 (AI Agent) 代理型AI (Agentic AI)
    启动类型 由用户或输入触发提示 由提示或工具使用触发目标 由目标发起或编排任务
    交互方式 User → LLM User → Agent → Tool User → System → Agents
    目标灵活性 (无) 每个提示固定 (低) 执行特定目标 (高) 分解和调整目标
    时间连续性 无状态，单会话输出 任务内的短期连续性 在工作流阶段中持续存在
    记忆使用 无记忆或短上下文窗口 可选的记忆或工具缓存 共享情景/任务记忆 (Shared episodic/task memory)
    协调策略 无 (单步流程) 孤立的任务执行 分层或去中心化协调
    角色 内容生成器 基于任务的执行器 协作工作流编排器
    1. Agentic AI在技术层面上的增量
    • 各代理与角色绑定
    • （更强的）推理与规划能力（e.g., 通过ReAct、CoT等）
    • 持久内存架构
    • 元代理/任务编排者
    1. Agentic AI面临的挑战（如果没有针对代理角色定义、通信标准、分层规划、应急措施等的稳健框架，Agentic AI并不一定意味着更高的智能或更强的稳健性）
    • 系统稳健性：
      • 单代理中的因果推理缺失问题放大
      • 对单点的对抗或攻击破坏正规系统安全性
      • 非预期系统行为偏离设计目标，破坏可用性（e.g., 无限规划，行动死锁或矛盾）或产生有害行为
    • 协作瓶颈
      • 多个代理间的歧义、竞争等，看法不对齐（value misalignment and drift）
    • 解释与调试维护性差：
      • 溯源、问责及形式化安全保障更困难
    1. 解决方案
    • RAG：减少幻觉和上下文的不一致，减少Agent间错误信息传播
    • 明确的角色分工：各功能模块化设计，每个Agent用于处理特定的预定义子功能；在工作流中整合函数/API调用，每个角色有特定、明确的调用能力；引入基于角色的访问控制、沙箱等
    • 主动反思、自我批评：如ReAct，作用在系统级别；或不同Agent间交叉审核（与上一点存在一定冲突）
    • 程序化/模板化的提示词，增强任务的一致性与工作流语义的一致性
    • 结合因果建模或仿真计划：通过因果图、仿真或贝叶斯等
    • 审计：日志记录等，用于提升可解释性和可追溯性

  • LLM App构建框架（以LangChain为例，但概念/方法是通用的）
    • Model: 统一的API接口
    • Prompt：Description（如，角色，能力），Context（直接指定，或来源于外部），User Input，Output demo/Example，通常模板化再使用
    • Chain：将Prompt，Model，Retriever等组件组合起来以执行连贯操作，将步骤模块化。（V.S. workflow: Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks）
    • Index：各种外部数据源，包括文档加载器、向量数据库、SQL等，支持文本分割器和RAG
    • Memory：默认无记忆。可选Last-K，Summary-based，或二者的组合（长期记忆用Summary，近期选取Last K）
    • Agent：Agent使用特定LLM作为推理引擎，确定Action，实现动态任务执行。输入包括User Input，Tool List，Memory等
      • 策略：ReAct，Self-Ask，Plan-and-Solve等，可组合
      • Tool可以使用预置的，也可以自定义，本质上是一个str到str的function（如，计算圆面积）

  • 3FS分布式文件系统 (Ref)： 
    graph TD
Client --> Mgmtd
subgraph "Mgmtd as a router"
Mgmtd -.-> Meta
Mgmtd -.-> Storage
end
    • Client：请求Mgmtd发现节点，请求Meta执行文件操作
    • Mgmtd：管理节点，类似于路由器，定期向Meta和Storage节点发送心跳以确认它们处于活动状态
    • Storage：保存实际数据。数据存取按链式（CRAQ）进行，链尾始终包含最新提交的数据。正向写入时中间节点数据标记为dirty，到链尾后反向向前commit，并flip dirty为clean。clean的数据可以安全返回Client。优点是可拓展、低延迟读取，代价是写入延迟较高（所有节点延迟的总和）
    • Meta: 元数据，例如权限、TS、大小等

5.7

  • 训练的几种并行方式：
    • Data Parallelism（数据并行）：不同device处理不同的数据子集、分别计算梯度，之后再同步梯度
    • Model Parallelism（模型并行）：将模型拆分到多个device，例如将Transformer的编码和解码器拆分的层间并行，或将矩阵乘法按行列拆分的层内并行（亦称张量并行）
    • Pipeline Parallelism（流水线并行）​：将模型按层拆分，同时将mini-batch进一步划分为若干micro-batch，可减少Pipeline Bubble（流水线气泡，即空闲时间窗口）
  • Batch Norm
    • 优点：平滑优化过程、减轻梯度消失，加快收敛，允许更大学习率，在batch较大且数据分布稳定时可加速训练
    • 缺点：batch size过小可能加剧噪声、降低效果，不适合输出分布不稳定（如GAN）或变化（如在线学习）的情形

4.7

  • Java中，匿名表达式中的变量和匿名表达式外部的引用（下例中的list）并不是同一个，而是复制了一个新的引用。因 此，匿名表达式中的变量必须是final或等同final的，以避免内部修改，外部不变的不一致情形 Workaround：
    • 匿名体前复制变量到一个新的final变量
    • 使用循环等非lambda方式
    • Lambda仅保证变量引用的不可变性，不限制对象状态的修改。因此修改引用变量成员是ok的，不过可能导致线程安全问题（并发修改、竞争）
